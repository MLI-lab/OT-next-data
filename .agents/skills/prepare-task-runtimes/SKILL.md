# Prepare task runtimes and check verifier dependencies

Use one workflow for offline setup and verifier dependency integrity. Work in
OT-next-data, modifying each datasource's existing patcher individually. Do not
build a blanket converter. An audit-only request does not authorize repairs or
publication. Creating this skill does not itself start a dataset audit.

## Establish scope and implementation support

Read the repository's `.agents/AGENTS.md`, root README sections on offline
compatibility and verifier execution, and
`harbor_patches/docs/prepared-verifier-runtimes.md`. Paths here are repo-relative.
For patch/report mechanics consult `.agents/skills/patch-dataset/SKILL.md`; for
validation consult `.agents/skills/verify-dataset/SKILL.md` and the current protocol.

The README runtime convention is a target design, not proof of implemented
behavior. Inspect `data/utils/verifier_runtime.py`,
`harbor_patches/{task_runtime,verifier_bundle,verifier_mount,verifier_setup}.py`,
`hpc/offline_prep/verifier_bundles.py`, and `hpc/offline_prep/verifier_offline.py` before using their APIs.
In particular verify preparation mode, cache naming, fallback installation,
manifest schema, writable defaults, and remote artifact handling. If support is
missing, implement and test the shared support first when authorized to repair;
otherwise report the gap. Never invent flags or emit manifests the runner cannot
read. Preserve compatibility with existing tasks and caches.

For “all v1”, enumerate the integrated datasource patchers and the actual `_v1`
directories in `FWeindel/validated-tasks` at a recorded immutable HF revision.
Reconcile differences and account for every requested dataset and task. Do not
treat an inventory's historical validation result as a current audit. Record
source revision, patch revision, task counts, and execution mode in the report.
Do not silently expand a v1 request to v2/v3.

## Apply the agreed convention

Prepared runtimes are optional. Tasks with no dependency setup, or whose required
dependencies and assets are already available offline, need no new runtime or
manifest solely for offline compatibility. Preserve their existing setup and
execution behavior; record “no additional preparation needed” with evidence.
Do not add empty setup scripts or runtime artifacts just to standardize tasks.
Check verifier dependency integrity separately: packages already in an image may
work offline but still be agent-modifiable in shared mode. Add protection only
where that review identifies a need, preserving intentional task modifications.

- Dependencies have one source of truth in setup's definitions, generated by
  the datasource patch if appropriate. Setup still performs other initialization.
  Give the setup script an explicit way to prepare reusable dependencies online
  and save them, without running grading or saving task-specific state. Use shared
  preparation helpers; document the actual executable command for each datasource.
- Preparation writes `setup_files/ot-task-runtime.json` for agent dependencies
  or `tests/ot-verifier-runtime.json` for verifier dependencies. The target
  reference contains an ID, archive checksum, and runtime options, not a duplicated
  package list or machine-specific path. Keep build provenance and resolved
  dependency versions with the cached artifact. If current APIs embed specs,
  migrate compatibly rather than removing required fields from generated tasks.
- Use `$OT_WORKSPACE/runtimes`, overridden by `OT_RUNTIME_CACHE`, once supported.
  Artifacts can be published under the HF repository's shared `runtimes/` folder.
  A user must also be able to regenerate them on another node/account. Rebuilt
  bytes may differ: produce matching checksums and references, and never overwrite
  an existing artifact identity with conflicting contents.
- Normal setup uses prepared dependencies or falls back to installation when
  missing/incomplete. Reject checksum-invalid bytes before use and try installation
  instead. Retain `set -e` and setup failure reporting. Use local packages for
  offline fallback. Never convert failed installation into successful setup.
- Keep the shared base read-only and give agent and verifier independent private
  writable layers, discarded after the trial. Stage verifier dependencies after
  the agent finishes. Never save trial changes back to the cache. A fresh private
  extraction protects the archive but is not evidence that overlay mounts exist.
- Preserve installation order and task initialization. Use cached package files
  at original install points when ahead-of-time installation changes semantics.
  Include non-Python dependencies, build tools, data, and other downloads. Do not
  describe a wheel cache as a complete installed runtime.

## Share artifacts without changing tasks

Group identical dependency recipes across tasks and datasources. Include Python
and tool versions, resolved dependencies, architecture, ABI/libc and required
base-image compatibility in the reuse decision. Prefer existing verified artifacts.
Combine compatible dependency sets only after checking for changed behavior;
avoid an enormous universal runtime. Keep repositories, generated task files,
credentials and task-specific initialization out of reusable artifacts. Record
unique artifact count, stored bytes and reuse counts, not per-task duplicated size.

Handle `uvx`, `uv tool run`, pip, system packages and other installers according
to their actual behavior. Pin resolved tools and transitive dependencies; ensure
their invocation does not start a fresh network-dependent tool environment.

## Check verifier integrity

Inspect `[verifier].environment_mode`, all setup/test entrypoints, executable and
import resolution, plugins, and dependencies already installed in the image.
In shared mode, provide a fresh verifier runtime or clean reinstall of every
verifier dependency. “Requirement already satisfied” in an agent-writable
environment is not a clean reinstall. Fallback must also use a clean trusted
interpreter/installer and a private environment, not agent-modified tools.

Keep the verifier's Python version: a prepared runtime uses the exact version the
original verifier ran with, the image's interpreter for tests that ran on it, or
the version an installer such as `uvx --python` selected. Point `sys.executable`
uses in tests at the task interpreter they meant (for example `/usr/bin/python3`),
so the agent's scripts still run in the task environment.

Preserve packages and project files the task explicitly asks the agent to modify;
tests must evaluate the submitted changes. Record these exceptions and keep
trusted grading tools separate from the code under test. Separate mode also needs
review of transferred files and actual tool resolution; its name alone is not a
safety result. Report remaining shared-system risks without claiming complete
reward-hacking protection from runtime isolation alone.

## Verify and report

Use disposable trials for checks, never tamper with shared images or caches:

- Prepare online, then run agent setup and verification with networking disabled.
  Test regeneration into another empty cache and verification from that artifact.
  `--no-index` alone is not proof that all task execution works offline.
- Exercise missing, incomplete and checksum-invalid artifacts, successful fallback,
  and failing fallback. Verify failures surface as setup errors.
- Modify an agent-side verifier dependency and confirm verification uses clean
  tools. Check private installs cannot affect another trial or the cached digest.
  Confirm intended agent edits to the code under test are still evaluated.
- Preserve grading semantics through reference/no-op checks where applicable.
  Cover every distinct runtime/setup family and record exact task coverage. A
  sampled pilot does not establish that every v1 task passes offline execution.

For datasource validation, verify all required images in the target cluster's
cache before submitting; prepare missing images in separate image-only jobs and
set `OT_REQUIRE_PREBUILT_IMAGES=1`. Enable stage-1 absolute-path resolution with
recovery evidence and all default training checks, including reference leak
checking when stage 4 uses references. AI-detection checks are intentionally
excluded by user policy. Missing prerequisites are incomplete, not passed.

Produce a per-dataset report with task/runtime counts, execution modes, fixes,
offline and tampering-test evidence, exceptions, incomplete checks, reproducible
preparation commands, artifact IDs/checksums and storage totals. Use scoped
conclusions such as “verifier dependency checks passed for these tasks”, not
“all v1 datasets are safe”. Keep untested, failed and inherently online cases
visible. Update the existing patch reporting inputs and preserve task IDs.

Publish only within the user's authorized scope using the existing publication
workflow and authenticated user identity. Verify uploaded artifact bytes before
publishing task references to them. Report local, tested and published status
separately; a patch edit does not update the existing HF dataset.
